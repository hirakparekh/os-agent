What the numbers actually say about this architecture

Every figure below was measured against the system as it runs today, on a real Gmail account with real ingested mail — not a simulation, not a slide-deck estimate. Where a number is a known structural property of a compared architecture rather than something we built and ran, it's labeled that way instead of blended in.

The setup

14 real email threads, ingested via Gmail OAuth into a per-user SQLite entity graph, classified by a free-tier model (liquid/lfm-2.5-2.6b:free) through OpenRouter. 3 real questions asked through the live chat endpoint. This is a pilot-scale run, not a large-N study — see the methodology note at the end before repeating these numbers to someone who'll ask for error bars.

Where the tradeoff actually cuts against us limitation

A committee will ask what this costs, not just what it saves. Answer honestly:

Indexing is more expensive, not less. For the same 14 emails, this system makes 28 generation-class LLM calls (2 per email) against a vector-RAG baseline's 14 cheap embedding calls. We are not cheaper at index time — we are more expensive there, on purpose. The argument is that indexing happens once per email while questions happen repeatedly, so the savings compound at query time where usage is actually unbounded. That argument holds only if people ask more questions than they receive emails — reasonable for an active chat user, not guaranteed.
Fixed schema, bounded recall. A category tree can't absorb something that fits no existing bucket as gracefully as open-ended retrieval can. This is a deliberate scope choice for a known domain (a student inbox has a small number of real categories), not a claim that the approach generalizes to an arbitrary unknown corpus.
A real bug this benchmark surfaced. Thread mail:thread:156 — a Google security alert from higgsfield.ai — was filed under "Placements" instead of a security/account category. The sender-precedent rule saw other real placement mail from the same domain and overrode a should-be-obvious classification. We're disclosing it, not hiding it: it's a live, reproducible finding, and it's the kind of error an opaque vector index would never surface for inspection in the first place, because there'd be no clickable tree node to notice it in.

Methodology note

n=14 threads, n=3 questions, one real inbox, one pilot run. This is directionally consistent with the architecture's design (fewer query-time calls, a working correction mechanism), but it is not a large-N study and the guardrail catch rate (36%) should be read as "observed in this inbox," not a general accuracy claim, until validated on a larger and independently-labeled sample.
